## 1. Summary

The game now opens on a real main menu: dark charcoal screen, ASCII rain, a left-aligned vertical menu, and
Continue / New Game / Load / Settings / Exit that appear according to the real state of three save slots.
New Game and Load both go through a slot picker with overwrite/delete confirmations, deleting every save hides
Continue and Load immediately without a restart, and gameplay still runs on the existing CleanRoom / Room3D flow.
Save files are now `slot1..3.json`; a pre-3.5 `save.json` is migrated into slot 1 once.

## 6. Main menu flow

- **Continue** → loads the newest valid slot (`SavedAtUtcTicks`), or reports a reason and refreshes if the target
  is no longer loadable.
- **New Game** → slot picker → confirm (empty) or overwrite warning (occupied) → writes a fresh profile to that
  slot only → sets the active slot → opens `Room3D`.
- **Load** → slot picker → valid slot loads; corrupted/incompatible shows the real reason; delete sits beside it.
- **Settings** → panel states plainly that no persisted settings system exists yet (no fake controls).
- **Exit** → confirmation → `Application.Quit()` (a no-op in the Editor, by design).
- Escape closes a dialog (cancel), then the slot/settings panel, and never quits from the main menu. Closing a
  panel returns focus to Continue (or New Game when Continue is hidden).

## 7. Dynamic visibility rules (implemented)

| Slot state | Continue | Load | New Game | Settings | Exit |
|---|---|---|---|---|---|
| ≥1 valid save | shown | shown | shown | shown | shown |
| only corrupted / incompatible | hidden | shown | shown | shown | shown |
| no save data at all | hidden | hidden | shown | shown | shown |

The controller re-reads slot files on every refresh, so deleting the last slot hides Continue and Load in the
same frame. Delete failures keep the row and show the error.

## 8. Save slot behavior

- States: Empty, Valid, Corrupted (unreadable), Incompatible (newer schema) — corruption is never reported as Empty.
- Inspect is read-only and falls back to the `.bak` exactly like the loader, so a recoverable slot is not shown as broken.
- Delete removes only that slot's files (`.json`, `.bak`, `.tmp`) with confirmation; a failed delete changes nothing.
- Continue targets the newest valid slot; ties fall back to the first slot found.
- `GameSession` never creates or overwrites a slot just by opening a scene, and it refuses to save when the slot
  failed to load (so a corrupt file is preserved for management).
- Metadata shown per slot: progress (chapter + completed missions), money, EXP, play time, last saved local time.
  Values come from the save file; nothing is mocked.

## 9. Digital rain implementation

18 reused `Text` columns, each a stack of ASCII glyphs (`01 {} <> IF AND NODE DATA EXEC …`). Columns scroll at
different speeds and re-randomise their glyphs a few times per second; `Time.unscaledDeltaTime` keeps it moving
even with `Time.timeScale = 0`. No per-frame instantiate/destroy, one reused `StringBuilder`, low density, and the
left half carries a scrim so the menu stays readable. The spec allows runtime generation for this dynamic visual.

## 11. Known limitations

- Settings is a clearly labelled placeholder; there is no persisted settings system to connect yet.
- Exit is only meaningful in a real build (`Application.Quit` is a no-op in the Editor).
- The main menu's visual quality (contrast, rain density, font sizes) was not verified by a screenshot in this
  environment; it needs one human look in the Game view at 16:9 and at 4:3/ultrawide.
- Controller/keyboard navigation relies on Unity's automatic vertical navigation between the visible buttons;
  a dedicated navigation graph is not authored.
- No audio hooks were added (no audio system exists yet).
- Save schema stayed at version 1 with appended fields; future incompatible saves are detected through
  `SchemaVersion`, not per-field.

## 12. Manual test steps

1. Empty save folder → open the game → only New Game / Settings / Exit.
2. New Game → slot 1 → confirm → room opens → accept a job → back to menu → Continue appears.
3. New Game into slot 1 again → overwrite warning → Cancel → slot unchanged.
4. New Game into slot 2 → both slots exist; Continue targets the newest save.
5. Load → pick slot 2 → gameplay loads that profile; slot 1 is untouched.
6. Delete slot 2 → confirm → it disappears; delete slot 1 → Continue and Load vanish immediately.
7. Corrupt `slot1.json` by hand → Load shows the slot as corrupted, Continue is hidden, New Game can still overwrite after confirming.
8. Build the player → Exit confirmation closes the application.
